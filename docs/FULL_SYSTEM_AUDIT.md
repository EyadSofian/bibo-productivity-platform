**الفرع:** `main` @ `44a8713` (شجرة نظيفة قبل بدء الأوديت)

## 1. Executive summary

النظام **بنيته سليمة وأمانه المعماري جيد** في معظم المواضع: عزل المستأجرين مطبق في SQL
على كل مسار قراءة، والتحكم عن بُعد يشترط موافقة الجهاز ويسجّل audit، والالتقاط المتكرر
idempotent عبر `client_uuid`. لوحة الإدارة متجاوبة فعلًا وRTL يعمل بشكل صحيح — لم أجد
مشاكل overflow أو overlay على أي من المقاسات المطلوبة.

المشاكل الحقيقية ليست في التصميم، بل في **ثلاث نقاط جوهرية**:

1. **"العرض المباشر" ليس مباشرًا.** المسار الحالي يعطي إطارًا كل **20 ثانية** (0.05 FPS)،
   وزمن أول إطار **حتى 19 ثانية** لأن الوكيل لا يعرف بالطلب إلا في نبضته التالية (كل 15
   ثانية). الهدف المطلوب (<3 ثوانٍ للبدء، <1 ثانية latency) بعيد بعامل 6–19×.
   قناة `remote-assist` أفضل (1.1 FPS) لكنها لا تعمل إلا داخل جلسة تحكم عن بُعد.

2. **لا يوجد نموذج زمني للخمول إطلاقًا.** لا جدول ولا عمود يسجّل idle / lock / sleep /
   offline تاريخيًا. النبضة تحمل الحالة *اللحظية* فقط وتُكتب فوق سابقتها. لذلك
   "وقت الخمول" و"إجمالي وقت الجهاز" و"أول/آخر نشاط" **غير قابلة للحساب اليوم** — وهي
   مطلوبة صراحة في ملف الموظف. كذلك لا يوجد عدّ clicks أو scrolls.

3. **إطارات البث تُخزَّن في Postgres كـ`bytea`**، وهو أغلى مسار ممكن: قياسًا، 200 إطارًا
   لصف واحد يتركان **12–36 ميجابايت** من TOAST الميت و**65 كيلوبايت WAL لكل إطار**.

وأخطر ثغرة أمنية مؤكدة عمليًا: **تحديد معدل تسجيل الدخول يمكن تجاوزه بالكامل** برأس
`X-Forwarded-For` مزوّر، لأن Gin يثق بكل proxy افتراضيًا (§6، P0-4). أثبتُّ ذلك بـ20
محاولة ناجحة مقابل 5 فقط من IP حقيقي.

**الحالة القاعدية للاختبارات:** 311 اختبارًا كلها ناجحة (Go 80 · Web 115 · Extension 63
· Rust 53). لا فشل، لا تخطٍّ. لكن التغطية غير متوازنة: `handlers` 5.7% و`middleware`
و`retention` و`server` عند 0%.

## 2. Architecture map — المسار الفعلي

المسار المطلوب توثيقه، كما هو في الكود فعلًا (لا كما في `README`):

```
┌─ Windows / macOS agent ─ apps/desktop/src-tauri ────────────────────────────┐
│                                                                             │
│  trackers::run()          POLL=1s   → WindowTracker::tick()                 │
│    platform::idle_seconds()         → active = idle < threshold             │
│    platform::active_window()        → (app_name, title, pid)                │
│    ⤷ chunked at MAX_CHUNK_S=60s     → storage::insert_activity_sample()      │
│                                                                             │
│  keystroke counter        KEY_FLUSH → counts only, never content            │
│  screenshot loop          interval  → capture_once() → WebP ≤50 KiB on disk  │
│  server::mod.rs (axum, 127.0.0.1)   ← Chrome extension /ingest (token)       │
│                                                                             │
│  storage/mod.rs = local SQLite queue (client_uuid = natural key, durable)    │
└────────────────┬────────────────────────────────────────────────────────────┘
                 │
   ┌─────────────┴──────────── HTTPS, Bearer JWT ────────────────────────────┐
   │                                                                          │
   │  sync/worker.rs   → POST /v1/sync/batch        (activity+keys+browser)    │
   │  sync/worker.rs   → POST /v1/sync/screenshots  (multipart WebP)           │
   │  sync/presence.rs → POST /v1/presence/heartbeat  every 15s                │
   │                     ⤷ response.capture_requested → capture_requested_frame│
   │  sync/remote_assist.rs                                                    │
   │       GET  /v1/devices/:id/remote-assist/pending   poll 2s (idle)         │
   │       POST /v1/remote-assist/:id/decision         employee consent        │
   │       GET  /v1/remote-assist/:id/actions?after=N   poll 180ms  ← INPUT    │
   │       POST /v1/remote-assist/:id/frame             every 900ms → VIDEO    │
   └──────────────────────────────┬───────────────────────────────────────────┘
                                  │
┌─ Backend ─ apps/backend (Gin + pgx, one binary also serves /admin) ─────────┐
│  handlers/sync.go       → activity_samples · keystroke_buckets ·            │
│                            browser_visits          (UPSERT on client_uuid)  │
│  handlers/screenshot.go → screenshots table + filestore (on disk, NOT db)   │
│  handlers/presence.go   → devices.presence_* columns (OVERWRITTEN each time)│
│  handlers/remote_assist.go → remote_assist_sessions / _frames / _actions /  │
│                              _audit         ⚠ frames are bytea IN POSTGRES  │
│  handlers/reports.go    → read path, tenant-scoped by b.owner_user_id       │
└──────────────────────────────┬─────────────────────────────────────────────┘
                               │  JSON + authed image GETs
┌─ Dashboard ─ apps/web-admin/src/pages/EmployeeDetail.tsx ───────────────────┐
│  presence poll         15s   reportPresence()                               │
│  LIVE VIEW (non-remote):                                                    │
│     requestLiveCapture()      every 20s  ← ceiling on frame rate            │
│     reportScreenshots()       every  3s  ← full report query, per viewer    │
│     fetchImageObjectUrl()     per new frame                                 │
│  REMOTE CONTROL:                                                            │
│     getRemoteAssist()         every  1s  (session status)                   │
│     fetchRemoteAssistFrameObjectUrl() every 900ms                           │
│     sendRemoteAssistAction()  on click / keypress (fire-and-forget)         │
```

**البروتوكول المستخدم: HTTP polling فقط. لا WebSocket ولا WebRTC في أي مكان من النظام.**
تحققت من ذلك بفحص جدول المسارات كاملًا في `apps/backend/internal/server/server.go:1-200`
— لا `Upgrade`، لا `gorilla/websocket`، لا SSE.

### 3.2 تكلفة التقاط الإطار على الوكيل — مقيسة

الأمر (اختبارات جديدة أضفتها، مُستثناة افتراضيًا):
```bash
cargo test --release -- --ignored --nocapture capture_cost
```
المصدر: `apps/desktop/src-tauri/src/trackers/mod.rs` (دالة `compress_webp_to_limit`).
الصورة المصدر 2560×1440 RGBA.

| القياس | الحالة المواتية | **الحالة السيئة** |
|---|---|---|
| سُلَّم إطار remote كاملًا | **63.7 ms** → 1600×900، 59 KiB | **456.3 ms** → 178 KiB |
| سُلَّم اللقطة الدورية | 60.3 ms → 1366×768، 23 KiB | **457.3 ms** → 1152×648 |
| تصغير واحد 2560×1440→1600×900 | 19.6 ms | — |
| ترميز WebP واحد @1600×900 | 44–46 ms (لكل درجة جودة) | — |

**الدلالة:** الفاصل بين الإطارات `FRAME_INTERVAL = 900ms`
(`sync/remote_assist.rs:22`). في الحالة السيئة الترميز وحده يستهلك **456/900 = 51% من
نواة كاملة** على أسرع عتاد متاح. على لابتوب مكتبي Windows نموذجي (أبطأ 3–4× في الأداء
أحادي النواة) تصبح التكلفة **1.4–1.8 ثانية للإطار الواحد** — أي أطول من الفاصل نفسه،
فتشبع النواة ويتأخر البث تراكميًا.

**السبب الجذري:** السُلَّم يجرّب 4 أبعاد × 5 درجات جودة = حتى **20 عملية ترميز WebP
كاملة + 4 عمليات تصغير** لإطار واحد، ويعيد أول نتيجة تحت السقف.

### 3.3 تكلفة كتابة الإطار في Postgres — مقيسة

قياس مباشر بنفس عبارات `store.SaveRemoteAssistFrame` على جدول منفصل بنفس الشكل:

| حجم الإطار | متوسط الكتابة | الأسوأ | الإنتاجية | **بعد 200 upsert لصف واحد** |
|---|---|---|---|---|
| 59 KiB | 336 µs | 2.25 ms | 2975/s | heap 1 صفحة · **TOAST 1534 صفحة · 12 MB** |
| 178 KiB | 463 µs | 2.76 ms | 2160/s | heap 1 صفحة · **TOAST 4600 صفحة · 36 MB** |

**WAL: 65.3 KiB لكل إطار** (مقيس عبر `pg_wal_lsn_diff` على 100 إطار).

**الدلالة:** زمن الكتابة نفسه ليس المشكلة — **التضخم وWAL** هما المشكلة. جلسة تحكم واحدة
مدتها 15 دقيقة عند 1.1 FPS ≈ 1000 إطار ⇒ **~60 MB من TOAST الميت و~65 MB من WAL**،
مقابل صف حي واحد. عشر جلسات متزامنة ⇒ 600 MB churn وضغط autovacuum مستمر، وعلى Postgres
مُدار (Railway) يُحتسب WAL في النسخ الاحتياطي والنسخ المتماثل. البيانات **عابرة بالتصميم**
(الإطار الأحدث فقط يُحتفظ به) — فلا مبرر لمرورها بالـWAL أصلًا.

## 4. المشاكل مصنّفة

### P0 — Critical

---

#### P0-1 — العرض المباشر ليس مباشرًا: إطار كل 20 ثانية وبدء حتى 19 ثانية

- **Symptom:** الشاشة "المباشرة" تتحدّث مرة كل 20 ثانية، وأول إطار قد يتأخر 19 ثانية.
- **Root cause:** ثلاثة سقوف متتالية — الوكيل لا يعرف بالطلب إلا في نبضة الـ15 ثانية،
  اللوحة تطلب إطارًا جديدًا كل 20 ثانية، وتكتشفه بـpolling كل 3 ثوانٍ. لا توجد قناة
  دفع (WebSocket/SSE) إطلاقًا.
- **Evidence:** §3.4. `sync/presence.rs:17` · `EmployeeDetail.tsx:240-241` ·
  `store/device.go:212-215` (دمج الطلبات خلال 10 ثوانٍ).
- **Affected files:** `apps/desktop/src-tauri/src/sync/presence.rs` ·
  `apps/web-admin/src/pages/EmployeeDetail.tsx:249-298` ·
  `apps/backend/internal/store/device.go`
- **Reproduction:** افتح ملف موظف متصل ← اضغط "ابدأ العرض المباشر" ← راقب `X-Frame-At` /
  زمن ظهور أول إطار في تبويب الشبكة.
- **Proposed fix:** قناة دفع للوكيل (SSE من الخلفية، أو WebSocket) بدل انتظار النبضة،
  + تقليل فاصل الإطار إلى ~1s أثناء المشاهدة النشطة فقط، + دفع الإطار للمتصفح بدل
  polling على تقرير اللقطات.
- **Regression risk:** متوسط — يمس مسار الالتقاط والوكيل معًا؛ يحتاج تحديث Agent.
- **Test required:** اختبار زمن أول إطار، واختبار أن الوكيل لا يلتقط عند عدم وجود مشاهد.
- **Acceptance:** أول إطار <3s على شبكة محلية؛ معدل مستقر ≥1 FPS.

---

#### P0-2 — لا يوجد نموذج زمني للخمول/القفل/النوم — نصف ملف الموظف غير قابل للحساب

- **Symptom:** لا يمكن عرض "وقت الخمول"، "إجمالي وقت الجهاز"، "أول/آخر نشاط"،
  "lock/unlock"، "sleep/wake"، أو خط زمني موحّد — لأن البيانات غير موجودة.
- **Root cause:** النبضة تحمل الحالة اللحظية وتُكتب فوق سابقتها في `devices`
  (`store/presence.go:UpdatePresence`, `ON CONFLICT DO UPDATE`). لا يوجد جدول
  `os_states` ولا سجل تاريخي. `activity_samples` تسجّل الفترات **النشطة فقط**؛ الخمول
  هو غياب صفوف، وهو غير قابل للتمييز عن إغلاق الجهاز أو انقطاع الشبكة.
- **Evidence:** لا يوجد أي جدول للحالات في `internal/db/migrations/*` (18 هجرة، فُحصت
  كلها). `trackers/mod.rs:901` التعليق نفسه يقر: *"Idle covers screen-locked /
  display-asleep too"* — أي أنها مدموجة عمدًا وغير قابلة للفصل.
- **Affected files:** `apps/backend/internal/db/migrations/` ·
  `apps/desktop/src-tauri/src/trackers/mod.rs:892-918` · `src/sync/presence.rs`
- **Proposed fix:** هجرة `000NN_os_states.sql` بجدول فترات
  `(user_id, device_id, state, started_at, ended_at, source)` حيث
  `state ∈ active|idle|locked|sleeping|offline`، يكتبه الوكيل كفترات مغلقة عبر
  `/sync/batch` بنفس نمط `client_uuid` الـidempotent.
- **Regression risk:** منخفض (إضافة فقط، لا تغيير في الجداول القائمة).
- **Test required:** اختبارات وحدة لآلة الحالات (نشط ساعة، خمول في المنتصف، sleep/wake،
  انقطاع ثم عودة، إعادة إرسال نفس الدفعة).
- **Acceptance:** `active + idle + offline = wall clock` لأي نطاق زمني، ±1%.

---

#### P0-3 — سُلَّم ضغط الإطار يستهلك حتى 51% من نواة (وأكثر من 100% على عتاد Windows نموذجي)

- **Symptom:** استهلاك CPU مرتفع على جهاز الموظف أثناء البث، وتأخر تراكمي في الإطارات.
- **Root cause:** `compress_webp_to_limit` تجرّب حتى 4 أبعاد × 5 درجات جودة = 20 ترميزًا
  كاملًا + 4 عمليات تصغير لكل إطار، بلا أي تكيّف أو ذاكرة للإعداد الذي نجح آخر مرة.
- **Evidence:** §3.2 — **456 ms/إطار** مقيسة في الحالة السيئة مقابل فاصل 900 ms.
- **Affected files:** `apps/desktop/src-tauri/src/trackers/mod.rs:621-661`
- **Proposed fix:** تذكّر آخر (بُعد، جودة) ناجح والبدء منه؛ بحث ثنائي بدل خطي؛ تقدير
  الحجم قبل الترميز الكامل. إضافةً: `adaptive quality` حسب زمن الرفع الفعلي.
- **Regression risk:** منخفض — الدالة نقية ومختبَرة.
- **Test required:** الاختبارات المضافة في §3.2 كحارس انحدار (سقف زمني).
- **Acceptance:** ≤120 ms/إطار في الحالة السيئة على نفس العتاد.

---

#### P0-4 — تجاوز كامل لتحديد معدل تسجيل الدخول عبر `X-Forwarded-For` (مؤكَّد عمليًا)

- **Symptom:** تخمين كلمات المرور غير محدود المعدل على الإنتاج.
- **Root cause:** `SetTrustedProxies` لم تُستدعَ إطلاقًا ⇒ Gin يثق بكل proxy افتراضيًا
  ⇒ `c.ClientIP()` يقرأ `X-Forwarded-For` من العميل ⇒ العميل يختار مفتاح الـlimiter.
  الإنتاج خلف Cloudflare Tunnel، فالرأس موجود ومُوثوق به فعلًا.
- **Evidence — أثبتُّه على الخلفية الحيّة:**
  ```
  A) نفس الـIP بلا XFF:      401 ×5 ثم 429 ×15   ← الحد يعمل
  B) نفس العميل مع XFF دوّار: 401 ×20             ← الحد متجاوَز بالكامل
  ```
- **Affected files:** `apps/backend/internal/middleware/ratelimit.go:22-34` ·
  `apps/backend/internal/server/server.go:31` (حيث يُبنى الـengine)
- **Reproduction:** الحلقتان أعلاه بـ`curl` على `/v1/auth/login`.
- **Proposed fix:** `r.SetTrustedProxies(nil)` (أو قائمة صريحة بشبكة الـproxy)، وعند
  استخدام Cloudflare اعتماد `TrustedPlatform` على رأس موثوق مثل `CF-Connecting-IP`.
- **Regression risk:** منخفض، لكنه يغيّر الـIP المُسجَّل في اللوجات — يجب التحقق بعد النشر.
- **Test required:** اختبار middleware يؤكد أن XFF المزوّر لا يغيّر مفتاح الـlimiter.
- **Acceptance:** الحلقة (B) تُنتج 429 بعد 5 محاولات.

#### P1-3 — التقاط الإطار يستخدم أول شاشة، والإدخال يذهب إلى الشاشة الأساسية

## 11. ما لم أستطع قياسه، ولماذا

بصراحة، حتى لا يُبنى قرار على رقم غير موجود:

- **كل قياسات Windows الحقيقية:** الجهاز هنا macOS. `execute_remote_action` كلها
  `#[cfg(target_os = "windows")]` — **لم تُترجَم ولم تُنفَّذ في هذا الأوديت إطلاقًا**.
  لذلك P1-3 (الشاشات المتعددة) و DPI scaling وتخطيطات لوحة المفاتيح مُشخَّصة بقراءة
  الكود ومواصفات Win32، لا بقياس.
- **زمن الرحلة الفعلي عبر الشبكة** (capture→server→browser): يحتاج وكيلًا حقيقيًا يبث؛
  ما قِسته هو تكلفة كل مرحلة على حدة + الفواصل المبرمجة، وجمعتها في ميزانية §3.4.
- **FPS الفعلي للعرض والرسم في المتصفح، والإطارات المفقودة/المكرّرة، وعدد إعادة
  الاتصال:** لا يوجد بث حي لقياسه. الأرقام في §3.4 **سقوف مشتقة من الكود** لا قياسات
  ميدانية — وهي كافية لإثبات فشل الهدف، لكنها ليست قياس أداء ميداني.
- **الشبكة البطيئة وفقد الحزم:** تحتاج بيئة throttling لم أُنشئها بعد.
- **تدقيق التبعيات:** لم يُشغَّل.

## 12. الخلاصة

المشروع أقوى مما يوحي به الطلب في جانبَي **التصميم والأمان المعماري**، وأضعف مما يبدو
في جانبَي **البث ونموذج الوقت**. لا يحتاج إعادة بناء ولا إعادة تصميم — يحتاج:

1. سد ثغرة حد المعدل المؤكَّدة (ساعة عمل، backend فقط).
2. بناء نموذج الحالات الزمنية الغائب — وهو **الحجر الأساس** لنصف ملف الموظف المطلوب.
3. إعادة هندسة مسار البث من polling بطيء إلى قناة دفع.

وكل ما عدا ذلك تحسينات تراكمية فوق بنية سليمة.

**قرارات التصميم المهمة:**

1. **الفترات متلاصقة ولا تتداخل** — الضمان الذي يجعل الأرقام قابلة للثقة:
   `active + idle + suspended + offline = الزمن المنقضي` بالضبط.
2. **المدة من حساب الساعة الفعلية** (`now - start`) لا من عدّ الدورات — وهو إصلاح ضمني
   لـP2-2 في المسار الجديد (المسار القديم `WindowTracker` ما زال يعدّ الدورات).
3. **backdating لحظة الخمول:** الانتقال إلى idle يُسجَّل عند لحظة توقف الإدخال فعليًا
   (`now - threshold`) لا عند لحظة *اكتشافه*، وإلا لضُخِّم وقت النشاط بمقدار threshold
   عند كل انتقال. مغطى باختبار مخصص.
4. **`offline` ليست حالة يبلّغ عنها الوكيل** — وكيل مقطوع لا يستطيع الإبلاغ عن انقطاعه.
   تُشتق في الخادم من الفجوات، وتُقصّ على الجزء المنقضي من النافذة فقط (فلا يُحسب باقي
   اليوم "غير متصل").
5. **`suspended` تغطي النوم والإسبات وإيقاف الوكيل** — الوكيل يعرف أن وقتًا مرّ بدونه،
   ولا يعرف السبب، فلا يدّعي معرفته.
6. **التوافق الخلفي:** الحقل اختياري في الطلب والاستجابة. وكيل قديم لا يرسل شيئًا،
   وخادم قديم يتجاهل الحقل ويترك الصفوف pending بدل وسمها مُزامَنة خطأً.

**الاختبارات المضافة (15):**

  الطويلة · نافذة الـgrace.
